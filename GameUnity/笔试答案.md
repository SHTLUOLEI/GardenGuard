# 笔试题答案

## 第 1 题 一周交付排期

### 1. 逐日安排

| | 周一 | 周二 | 周三 | 周四 | 周五 |
|---|---|---|---|---|---|
| 主程 | A 存档与重开 | A 存档与重开 | B 平台接入 | D 集成回归 | 修 D 里的问题、出验收包 |
| 初级 | C 关卡配置 | C 关卡配置 | F 界面精修（第 1 天） | D 集成回归 | 配合修问题；没有问题再做 F 第 2 天 |

- 保留：A、B、C、D。A 和 C 没有依赖，两个人周一就各自开工，周二结束时都能做完；B 依赖 A，所以放周三；D 需要 A、B、C 都完成，周四两个人一起做。
- 延期：E。主程只有周五一天空着，这一天要留给 D 发现的问题和打包。E 是新战斗特效，最后一天加新内容很容易引入新 bug，不值得冒险。
- F 部分做：初级周三先做第一天。周五要看 D 的结果，回归没问题就做完 F，有问题就先修 bug，F 剩下的部分延期。

### 2. 三个检查点

- 周二下班：A、C 完成。要看到的东西：旧存档能读进来，杀进程重进最高分还在，重开流程走一遍没问题；关卡配置能正常导出，游戏里能读到。
- 周三下班：B 完成。要看到的东西：在目标平台上能装上能跑的包，切后台、回前台这些平台回调正常。
- 周四下班：D 完成。要看到的东西：回归清单的执行结果，问题列表和各自的严重程度，一个候选验收包。阻塞性的问题必须在这时候已经发现，周五只用来修。

### 3. B 从 1 天变成 2 天

在发现的当天就同步，不等到周三晚上的检查点。B 一开工就要判断工作量，最晚周三中午能看出来。

调整：

- B 改成周三、周四两天。D 只能挪到周五，周五就没有缓冲时间了。
- 初级周三、周四做完 F。周四可以先对 A 和 C 做一部分回归，把能提前测的先测掉，减轻周五的压力。
- 告诉负责人这个风险：周五的回归一旦发现阻塞问题，就没时间修了。给两个选择：一是周五照常交付，但可能带着已知问题；二是验收往后推半天到一天。由负责人来定。
- E 继续延期。

## 第 2 题 交付前的风险处理

### 1. 优先级和下午的分工

优先级：存档丢进度 > 美术推迟 > 排行榜。

- 存档丢进度最严重。线上玩家的数据丢了没法补，而且现在连原因都不知道，必须先处理。
- 美术推迟影响最小。先用占位资源，资源到了直接替换，不影响程序进度。
- 排行榜：两个人日，相当于本周剩下时间的一半，而且要联网，题目范围外还带来新风险。建议这一版不做，放到下个版本。

接下来半天：

- 主程：查存档。先找几份不同版本的旧存档稳定复现问题，在升级流程的读取、转换、写入几个点加日志，重点怀疑写到一半被打断（没有原子写入）、版本号判断不对、字段缺失时用了默认值把旧数据覆盖。
- 初级：收集各个版本的旧存档样本，给升级流程写测试用例；把占位资源接进去，保证包能正常打出来。

### 2. 风险同步消息

> 新版本升级旧存档时偶发丢进度，原因还在查，影响老玩家数据，是交付阻塞项。建议：周五按时交付，排行榜放下个版本，美术先用占位。今天 18:00 同步存档定位结果。

### 3. 到点还没找到原因的后备方案

不管原因找没找到，先保证玩家数据不会再丢：

- 升级前把旧存档原样复制一份做备份。
- 升级后的数据先写临时文件，读回来校验通过以后再替换正式存档。
- 校验失败或者读取异常，就自动回退到备份，下次启动重试，同时上报日志。
- 最坏情况：这一版关掉自动升级，继续用旧格式读写，等问题查清楚再上。

这样做至多是"这次没升级成功"，不会出现"进度没了"。同时和负责人说清楚，问题本身还没修，后续会接着查。

## 第 3 题 奖励重复发放

### 1. 根因

`+=` 和 `-=` 后面写的是两个 lambda。虽然写法一样，但它们是两个不同的方法，生成的也是两个不同的委托对象。`-=` 要找到相等的委托才能移除，找不到就什么都不做，也不报错。

所以每次 OnEnable 都多挂一个监听，OnDisable 一个也没摘掉。打开关闭一次，事件上就挂了两个监听，下次胜利加 200，之后继续往上累加。

另外 `RoundWon` 是静态事件，它会一直引用面板。面板销毁以后，事件触发还会调到已经销毁的对象上。

### 2. 最小修复

改成具名方法，订阅和取消用的就是同一个方法：

```csharp
void OnEnable()
{
    GameEvents.RoundWon += OnRoundWon; 
}
void OnDisable() 
{ 
    GameEvents.RoundWon -= OnRoundWon; 
}

void OnRoundWon() 
{ 
    AddCoins(100); 
}
```

如果一定要用 lambda，就把它存到字段里，订阅和取消都用这个字段。

### 3. 验证用例

1. 面板反复打开关闭 5 次，然后让它保持打开，触发一次 RoundWon，金币只加 100。
2. 面板打开后关闭（或者直接销毁），触发 RoundWon，金币不变，也不报错。

还可以加一条：检查 `RoundWon` 的调用列表长度，打开时是 1，关闭后是 0。

## 第 4 题 异步加载显示错误关卡

### 1. 原因

- 显示了关卡 1：两次请求同时在跑，谁后完成，谁就最后执行 `ShowLevel`。代码在 await 回来以后没检查这个结果还是不是玩家最后选的那个关卡，所以关卡 2 先完成、关卡 1 后完成，关卡 2 就被关卡 1 覆盖了。
- 遮罩一直在：`LoadAsync` 抛异常以后，后面的代码都不执行了，`SetActive(false)` 也跳过了。

### 2. 修复

每次请求拿一个序号，回来以后只有最新的请求才能改界面；关遮罩放进 finally。

```csharp
int m_requestId;

async Task OpenLevelAsync(int levelId)
{
    int id = ++m_requestId;
    loadingPanel.SetActive(true);
    try
    {
        var level = await loader.LoadAsync(levelId);
        if (id != m_requestId)
        {
            loader.Release(level);   // 过期的结果，丢掉并释放
            return;
        }
        currentLevel = level;
        ShowLevel(level);
    }
    catch (Exception e)
    {
        if (id == m_requestId) ShowLoadError(e);
    }
    finally
    {
        if (id == m_requestId) loadingPanel.SetActive(false);
    }
}
```

如果加载接口支持取消，新请求开始时再把旧请求 cancel 掉，省掉没用的加载。

### 3. 旧请求不要误关新请求的遮罩

就是上面 finally 里的那个判断：只有 `id == m_requestId` 的请求才能关遮罩。旧请求结束的时候，序号已经被新请求改掉了，它不会去碰遮罩，遮罩一直留到新请求结束才关。

如果多个加载确实需要并行（不是互相替代的关系），就改用计数：开始时加 1，结束时在 finally 里减 1，减到 0 才关遮罩。

## 第 5 题 性能问题定位

### 1. 先查什么

先查主线程上每帧的托管内存分配。

- GPU 从 8 ms 到 9 ms，基本没变，问题不在渲染。
- 主线程从 10 ms 涨到 26 ms，而且已经去掉了限帧等待，是实打实的 CPU 开销。
- 每帧 GC.Alloc 从 1 KB 涨到 90 KB。按 60 帧算，一秒就是 5 MB 多的垃圾，GC 会被频繁触发。GC 是一次性停住主线程的，正好对应"间歇性卡顿"和 P95 从 22 涨到 68 ms。

所以最可能的是新版本里有什么东西每帧在大量分配：LINQ、字符串拼接、装箱、每帧 new List 或数组、闭包、每帧改 UI 文本这类。

### 2. 接下来三步

1. 在真机上用 Development Build 连 Profiler 跑同一个压力场景。CPU Usage 按 GC Alloc 排序，找出每帧分配最多的函数；再挑几个卡顿帧，确认里面是不是 GC.Collect。需要更细的话，开 Deep Profile 或者分配调用栈。
2. 对照新旧两个版本的代码改动，重点看每帧都会跑的路径（Update、事件回调、UI 刷新）。定位不出来就用开关或者二分法把新改动逐个关掉，看分配和主线程耗时从哪一步降下来。
3. 改掉分配以后，再看主线程还剩多少。26 ms 里 GC 只占一部分，如果分配降下来了主线程还很高，就要接着查 CPU 本身多出来的计算。

### 3. 能不能说是内存泄漏

不能。GC.Alloc 说的是"每帧分配了多少"，不是"有多少没被释放"。分配多、但 GC 能收回去，只是产生垃圾快，不是泄漏。

要判断是不是泄漏，得看长时间运行以后，每次 GC 之后剩下的内存是不是一直在涨，或者对比两份内存快照，看是不是有不该存在的对象越积越多。现在两样都没有。

### 4. 修复后怎么验证

同一台真机、同一套构建配置、同一个压力场景、同样的时长，再测一遍，对比：

- 每帧 GC.Alloc 回到 1 KB 左右；
- 主线程平均耗时回到 10 ms 左右；
- 帧耗时 P95、P99 降下来，测试时段内 GC 次数明显减少；
- 跑长一点（比如 10 到 20 分钟），确认内存稳定、没有新的卡顿。

最好再加一个自动化的检查，把关键路径每帧分配不超过多少写成测试，以后再出现类似问题能直接发现。
