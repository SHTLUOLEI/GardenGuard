# 性能问题定位与优化：密集击杀时的卡顿（第 3 题）

## 测试条件

| 项 | 值 |
|----|----|
| 真机 | iQOO 9（骁龙 8 Gen 1），抖音开发者工具「真机调试 → 性能测试工具」 |
| 负载 | 压力场景 `Defense90Stress`：每批 8 只、同屏上限 512（正常场景每批 1 只、上限 256），随机种子 90，特效档位：普通 |
| Editor 基准 | i9-12900H，Unity 2022.3.62f3c1；固定输入：512 敌人 + 64 水花 + HUD/飘字，预热 20 次、采样 300 次 |
| 优化前数据 | 优化前包的开发者工具运行性能报告截图；优化前源码在 Editor 里用同一份固定输入跑基准 |

## 1. 问题现象和测量证据

**现象**：正常场景流畅；压力场景里敌人密集、炮塔连续击杀或技能同时命中大量敌人时，画面一顿一顿，手机明显发热。

**真机证据（优化前包，开发者工具运行性能报告）**：平均帧率 **49.18**（目标 60），卡顿率 **0.13%**，Unity Heap 184.375 MB，Heap grow 2 次（未通过）。

**Editor 固定输入定位**（同一份输入分别跑新旧两版代码）：

| 观测项 | 优化前 |
|--------|--------|
| 表现层刷新耗时，512 敌人 | 1.854 ms / 次（p95 2.336 ms） |
| 120 帧连续普攻中被顿帧冻结的帧 | **114 / 120** |
| 64 个水花使用的 MaterialPropertyBlock | 64 个（每个都打断合批） |
| 击杀时分数弹跳 | 每次新建 Punch Tween 及路径数组 |
| 命中音效 | 每次命中都 PlayOneShot，同帧叠加 |

## 2. 原因判断和修改方案

| 原因 | 修改 |
|------|------|
| **普通命中触发全场顿帧**。顿帧本来是技能的打击感设计，但普攻也会触发；压力场景命中频率高，画面几乎一直处于冻结状态。这是"卡"的主要来源，而且不是 CPU 不够，而是逻辑主动停帧 | 普攻不再顿帧，只保留技能命中的 45 ms 短顿帧；规则时钟、伤害、排序不变 |
| 每个水花用属性块单独设置进度，合批被打断，Draw Call 随水花数增加 | 进度写入顶点 alpha，所有水花共用一份材质 |
| 每个敌人每帧重复调用 `transform`、读取精灵尺寸等原生接口 | 缓存 Transform、精灵宽度、敌人状态与排序值；深度排序改为复用上一帧顺序的增量校正 |
| 每次击杀新建 Tween，同帧多次命中音效叠加 | 分数弹跳复用一个动效时钟；同类命中音效 50 ms 内合并 |
| 帧耗时超过 0.5 s 时自动弹出暂停页，加载尖峰会误触发 | 删除帧尖峰自动暂停，只保留切后台、失焦和手动暂停 |

## 3. 优化前后结果

**Editor 固定输入（同机、同输入，可重复）**：

| 指标 | 优化前 | 优化后 | 变化 |
|------|--------|--------|------|
| 表现层刷新，512 敌人 | 1.854 ms | 0.397 ms | −79% |
| 512 敌人 + 64 水花 + HUD/飘字 | 0.517 ms（p95 0.646） | 0.389 ms（p95 0.504） | −25% |
| 普攻顿帧帧数 / 120 帧 | 114 | 0 | 消除 |
| 水花属性块数 | 64 | 0 | 恢复合批 |
| 索敌（512 敌人） | 96.5 µs（LINQ 排序） | 9.4 µs（线性扫描） | −90% |

**Editor 压力场景 60 s 采样（优化后，游戏内性能面板）**：3600 帧，平均 16.7 ms，P95 18.7 ms，P99 19.7 ms，超过 33 ms 的帧 0 帧，同屏敌人峰值 287；分段 CPU 平均耗时：Battlefield 0.17 ms，HUD 0.02 ms。

**真机（开发者工具运行性能，压力模式完整一局）**：

| 指标 | 优化前包 | 第二轮包 | 当前包（第三轮） |
|------|----------|----------|------------------|
| 平均帧率 | 49.18 | 50.70 | 48.55 |
| 卡顿率 | 0.13% | 0.05% | **0.07%** |
| Unity Heap / grow 次数 | 184.375 MB / 2 | 184.375 MB / 2 | **128 MB / 0** |

**真机游戏内性能面板（当前包，压力模式 60 s，1080×2400，目标 60 帧；同一个包、同一台设备、同一时段，只切换特效档位）**：

注：这组档位对比是在糖果水特效改版之前测的，改版后的两档还没有重新测。

| 指标 | 普通档 | 简化档 |
|------|--------|--------|
| 帧耗时 avg / P50 | 17.4 / 17.0 ms | 17.5 / 17.0 ms |
| 帧耗时 P95 / P99 / max | 23.0 / 40.0 / 111.0 ms | 24.0 / 40.0 / 152.0 ms |
| 超过 33 ms 的帧 | 76 / 3440（2.2%） | 80 / 3428（2.3%） |
| 同屏敌人峰值 | 288 | 298 |
| 托管堆（窗口内增长 / 峰值 / GC） | +0.66 MB / 12.4 MB / 0 次 | +1.05 MB / 12.8 MB / 0 次 |
| Battlefield avg / max | 0.62 / 31.0 ms | 0.65 / 44.0 ms |
| HUD avg / max | 0.37 / 56.0 ms | 0.47 / 74.0 ms |
| FloatText avg / max | 0.09 / 4.0 ms | 0.01 / 1.0 ms（简化档关闭伤害飘字） |

**结论**：
- **卡顿改善**：卡顿率 0.13% → 0.07%。近 300 只敌人同屏时窗口内 GC 为 0 次，普攻不再冻结画面，击杀时一顿一顿的现象消失。
- **战斗中基本稳定在 60 帧**：P50 为 17.0 ms，接近 60 帧的帧间隔 16.7 ms，说明绝大多数帧已经达到目标帧率。开发者工具里 48.55 的平均帧率统计的是整段运行，包括首页和加载过程，不能直接等同于战斗帧率。
- **特效不是瓶颈**：普通档和简化档的帧耗时几乎一样（P95 23 vs 24 ms，P99 都是 40 ms）。FloatText 从 0.09 降到 0.01 ms，证明档位确实生效了。所以简化档对这台设备的帧率帮助有限，主要价值在更低端的机型。
- **内存改善**：Heap 184 MB → 128 MB，grow 2 → 0。这主要来自 WebGL 内存配置（初始内存固定为 128 MB）和资源压缩，不是本次战斗代码的贡献。
- **剩余问题是偶发长帧**：约 2% 的帧超过 33 ms，max 111~152 ms。两次测试中 HUD 单帧最高都在 56~74 ms，Battlefield 最高 31~44 ms，平均值却都不到 1 ms，说明是偶发尖峰，不是持续负载。推测 HUD 尖峰来自连击/分数文字变化时的字体网格重建，或者 WebGL 下 Stopwatch 计时被浏览器调度打断，需要用 Profiler 进一步确认。这是下一步的定位方向，本次没有处理。

## 4. 代价和限制

- **披露的改动**：第二轮把全局帧率上限从 120 改为 60，同时压缩了首页背景（仅 WebGL，上限 2048）；之后又调整了 WebGL 内存配置与包体。所以三个包的构建配置并不完全一致，真机差异不全来自代码优化，严格的单变量对比只有 Editor 固定输入那一组。敌人数量、伤害、刷怪节奏和分辨率都没有改；特效档位只在档位对比那一组里切换，其余测试都是普通档。
- **代价**：普攻失去顿帧，打击感变弱；同帧命中音效被合并，密集时音效层次减少；水花 Shader 同时维护顶点参数和统一参数两条路径，用测试保证两者一致。
- **限制**：
  - Editor 基准只覆盖 CPU 调用和人为顿帧，不包含手机 GPU、WebGL 桥接、音频解码和热降频。
  - 优化前包的真机报告没有记录场景和操作，也没有 P95/P99；当前包按压力模式完整一局测试，两者负载不能保证完全一致。
  - 真机测试经由开发者工具真机调试，调试连接本身有额外开销。
  - 只测了 iQOO 9 一台设备，没有覆盖低端机、iOS，也没有长时间的发热数据。
