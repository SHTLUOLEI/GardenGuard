# 笔试题作答

## 第 1 题 一周交付排期

**1. 逐日安排**

| | 周一 | 周二 | 周三 | 周四 | 周五 |
|---|---|---|---|---|---|
| 主程 | A | A | B | D | 修 D 发现的问题，出验收包 |
| 初级 | C | C | F（第 1 天） | D | 一起修问题，没问题就把 F 做完 |

A 和 C 都没有前置，周一两个人各做各的，周二下班都能完成。B 要等 A，放周三。D 要等 A、B、C 全部完成，周四两个人一起做。

A、B、C、D 全保留。E 延期：主程到周五才有空，但周五得留给 D 测出来的问题和打包，最后一天再加新的战斗特效，风险太大。F 做一半：初级周三先做一天，周五看回归结果，回归顺利就做完，有 bug 就先修 bug，F 剩下的延期。

**2. 检查点**

- 周二下班，看 A 和 C：旧存档能读进来，杀进程重进最高分还在，重开流程走一遍没问题；关卡配置能导出，游戏里读得到。
- 周三下班，看 B：目标平台上有一个能装能跑的包，切后台、回前台这类平台回调都正常。
- 周四下班，看 D：回归清单跑完的结果、问题列表和严重程度、一个候选验收包。阻塞问题必须在这个时间点之前暴露出来，周五只修不找。

**3. B 变成 2 天**

发现的当天就说，不等周三晚上的检查点。B 开工半天左右就能判断工作量，最晚周三中午就该知道。

调整的话，B 占周三、周四，D 只能挪到周五，周五就没有缓冲了。初级周三、周四把 F 做完，周四顺便把 A 和 C 能提前测的先回归掉，减轻周五的压力。E 照样延期。

然后跟负责人讲清楚：周五回归如果测出阻塞问题，就没时间修了。可以选周五照常交、带着已知问题交，也可以选验收往后推半天到一天，让负责人拍板。

## 第 2 题 交付前的风险处理

**1. 优先级和分工**

先处理存档，其次是美术，排行榜这一版不做。

存档丢进度最要命，玩家数据丢了补不回来，现在连原因都不知道。美术晚一天影响最小，先用占位资源，到了直接换，不耽误程序。排行榜要两个人日，差不多是这周剩下时间的一半，还要联网，又会带来新的风险，建议放到下个版本。

接下来半天：

- 主程查存档。先拿几份不同版本的旧存档把问题稳定复现出来，在升级流程的读、转换、写这几处加日志。我会先怀疑三个方向：写到一半被打断（没有原子写入）、版本号判断写错了、字段缺失时用默认值把旧数据盖掉了。
- 初级去收集各个版本的旧存档样本，给升级流程补测试用例；另外把占位资源接上，保证包能正常打出来。

**2. 风险同步**

> 新版本升级旧存档时偶发丢进度，原因还在查，影响老玩家数据，属于交付阻塞项。建议周五按时交付，排行榜放下个版本，美术先用占位。今天 18:00 同步存档的定位结果。

**3. 到点还没查到原因**

原因可以慢慢查，但先得保证玩家数据不会再丢：

- 升级之前，把旧存档原样复制一份备份；
- 升级后的数据先写到临时文件，读回来校验通过了再替换正式存档；
- 校验失败或者读取出错，就回退到备份，下次启动再试，同时把日志报上来；
- 实在不行，这一版先关掉自动升级，继续按旧格式读写，等问题查清楚再打开。

这样最坏也只是这次没升级成功，不会出现进度没了的情况。同时要跟负责人说明，问题本身还没修好，后面会继续查。

## 第 3 题 奖励重复发放

**1. 根因**

`+=` 和 `-=` 后面是两个 lambda，长得一样，但编译出来是两个不同的方法，委托对象也不是同一个。`-=` 要找到相等的委托才能移除，找不到就什么也不做，也不会报错。

结果就是每次 OnEnable 都多挂一个监听，OnDisable 一个都摘不掉。面板开关一次，事件上就挂了两个，下次胜利加 200，之后越开关越多。

还有一个隐患：`RoundWon` 是静态事件，会一直持有面板的引用。面板销毁之后事件再触发，还会调到已经销毁的对象上。

**2. 最小修复**

换成具名方法，订阅和取消用的是同一个方法：

```csharp
void OnEnable()
{
    GameEvents.RoundWon += OnRoundWon; 
}
void OnDisable() 
{ 
    GameEvents.RoundWon -= OnRoundWon; 
}

void OnRoundWon() 
{ 
    AddCoins(100); 
}
```

非要用 lambda 的话，就先把它存进一个字段，订阅和取消都用这个字段。

**3. 验证用例**

1. 面板反复开关 5 次后保持打开，触发一次 RoundWon，金币只加 100。
2. 面板打开后关掉（或者直接销毁），再触发 RoundWon，金币不变，也不报错。

还可以直接查 `RoundWon` 的调用列表长度，打开时应该是 1，关掉后是 0。

## 第 4 题 异步加载显示错误关卡

**1. 原因**

显示成关卡 1，是因为两个请求同时在跑，谁后完成谁最后调 `ShowLevel`。await 回来以后没有检查这个结果是不是玩家最后点的那一关，关卡 2 先加载完显示了，关卡 1 后加载完又把它盖掉了。

遮罩一直不消失，是因为 `LoadAsync` 抛了异常，后面的代码都不执行了，`SetActive(false)` 也被跳过了。

**2. 修复**

每次请求拿一个序号，回来的时候只有最新的那次请求才能改界面，关遮罩放进 finally：

```csharp
int m_requestId;

async Task OpenLevelAsync(int levelId)
{
    int id = ++m_requestId;
    loadingPanel.SetActive(true);
    try
    {
        var level = await loader.LoadAsync(levelId);
        if (id != m_requestId)
        {
            loader.Release(level);   // 结果已经过期，丢掉并释放
            return;
        }
        currentLevel = level;
        ShowLevel(level);
    }
    catch (Exception e)
    {
        if (id == m_requestId) ShowLoadError(e);
    }
    finally
    {
        if (id == m_requestId) loadingPanel.SetActive(false);
    }
}
```

如果加载接口支持取消，新请求开始的时候顺便把旧请求取消掉，省得白加载。

**3. 旧请求别关掉新请求的遮罩**

靠的就是 finally 里那个判断，只有 `id == m_requestId` 才能关遮罩。旧请求结束时序号已经被新请求改掉了，它碰不到遮罩，遮罩会一直留到新请求结束。

如果几个加载本来就要并行（不是后一个替换前一个），那就改成计数：开始时加一，finally 里减一，减到零才关遮罩。

## 第 5 题 性能问题定位

**1. 先查什么**

先查主线程上每帧的托管内存分配。

GPU 从 8 ms 到 9 ms，几乎没变，问题不在渲染。主线程从 10 ms 涨到 26 ms，而且已经排除了限帧等待，是实实在在多出来的 CPU 开销。每帧 GC.Alloc 从 1 KB 涨到 90 KB，按 60 帧算一秒就是 5 MB 多的垃圾，GC 会被频繁触发。GC 一跑就把主线程整个停住，正好对得上"间歇性卡顿"和 P95 从 22 涨到 68 ms。

所以我猜是新版本里有东西每帧都在大量分配，常见的就是 LINQ、字符串拼接、装箱、每帧 new List 或数组、闭包、每帧改 UI 文本这几类。

**2. 接下来三步**

1. 用 Development Build 在同一台真机上连 Profiler，跑同一个压力场景。CPU Usage 按 GC Alloc 排序，找出每帧分配最多的函数；再挑几个卡顿帧，看里面是不是 GC.Collect。不够细就开 Deep Profile 或者分配调用栈。
2. 对照新旧版本的改动，重点看每帧都会走的代码，比如 Update、事件回调、UI 刷新。还找不到的话，就用开关或者二分，把新改动一个个关掉，看分配和主线程耗时在哪一步降下来。
3. 分配修掉以后，再看主线程还剩多少。26 ms 里 GC 只占一部分，如果分配降了主线程还是高，就得继续查 CPU 本身多出来的计算。

**3. 能不能断言内存泄漏**

不能。GC.Alloc 说的是每帧分配了多少，不是有多少没被释放。分配得多但 GC 收得回来，只能说明垃圾产生得快，不算泄漏。

要判断泄漏，得看长时间运行后每次 GC 完剩下的内存是不是一直往上涨，或者拿两份内存快照对比，看有没有不该存在的对象越堆越多。这两样现在都没有。

**4. 怎么验证修好了**

同一台真机、同一套构建配置、同一个压力场景、同样的时长，再测一遍，对比这几项：

- 每帧 GC.Alloc 回到 1 KB 左右；
- 主线程平均耗时回到 10 ms 左右；
- P95、P99 降下来，测试期间 GC 次数明显变少；
- 多跑一会儿（10 到 20 分钟），内存稳定，没有新的卡顿。

最好再补一个自动化检查，比如给关键路径每帧分配量设个上限写成测试，以后再出类似问题能第一时间发现。
